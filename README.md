# 포켓몬 계단 레이스 — 설정·배포·테스트 가이드

2D Canvas 횡스크롤 계단 레이스 · 최대 20명 실시간 멀티플레이
**GitHub Pages + Firebase(Authentication, Realtime Database)만 사용 — 별도 게임 서버 없음**

---

## 1. 파일 구조

```
stair-race/
├─ index.html            화면 구조 (시작 / 대기실 / 게임 / 결과 / 모달)
├─ style.css             디자인 (PC·모바일 반응형)
├─ game.js               게임 로직 · 2D 렌더링 · Firebase 연동
├─ config.js             Firebase 설정값 · 관리자 이메일 · 게임 설정
└─ database.rules.json   Realtime Database 보안 규칙 (Firebase 콘솔에 붙여넣기용, Pages에는 올리지 않아도 됨)
```

`server.js` / `package.json`은 **만들지 않았습니다.** 아래 2번처럼 서버가 하던 판정을 보안 규칙이 대신합니다.

---

## 2. 서버 없이 어떻게 공정하게 판정하나요?

| 서버가 하던 일 | 이 프로젝트에서 담당하는 곳 |
|---|---|
| 공통 계단 코스 생성 | 관리자가 시작할 때 `seed` 하나만 저장 → 모든 브라우저와 **보안 규칙이 같은 수식**으로 계단 방향 계산 |
| 이동 검증 (방향·순서) | 보안 규칙: 계단 수는 **정확히 +1만** 허용, 방향이 코스와 다르면 **거부** |
| 입력 속도 제한 | 보안 규칙: 이동 간격 40ms 미만 거부 (Firebase 서버 시각 `now` 기준) |
| 서버 기준 타이머 | 시작 시각을 Firebase 서버 시각으로 기록, 카운트다운·종료 이후 이동은 규칙이 거부 |
| 추락·탈락 | 탈락(a=false)은 되돌릴 수 없음. 무입력 시간 초과 시 규칙이 이동을 거부하고, 모든 화면이 같은 기준으로 '탈락' 표시 |
| 관리자 권한 | 보안 규칙: `stairRace/admins/{UID} = true` 인 계정만 시작·종료·기록 저장 가능 |
| 정원 20명 | 보안 규칙: 슬롯 0~19만 존재, 1인 1슬롯 |
| 순위 | 규칙을 통과한 데이터만으로 모든 브라우저가 **같은 공식**(계단 수 ↓, 동점이면 먼저 도달한 사람)으로 계산 |
| 결과·개인 기록 저장 | 관리자 브라우저가 원자적으로 1회 저장, 같은 경기 중복 저장은 규칙이 거부 |

경기 진행(시간 흐름, 이동, 종료)은 **관리자 브라우저와 무관**합니다. 관리자가 새로고침하거나 창을 닫아도 경기는 계속되고 정해진 시각에 끝납니다.

## 3. Firebase Authentication 설정

1. [Firebase 콘솔](https://console.firebase.google.com) → 프로젝트 선택 (기존 게임들과 같은 프로젝트여도 됩니다)
2. **Authentication → 로그인 방법(Sign-in method)** 에서 두 가지를 **사용 설정**
   - **익명(Anonymous)** — 일반 참가자용. 같은 브라우저에서는 새로고침해도 같은 UID가 유지되어 진행 상황이 복구됩니다.
   - **이메일/비밀번호** — 관리자용
3. **Authentication → 사용자(Users) → 사용자 추가** 로 관리자 계정 생성
   - 가상 이메일 사용 가능: 예) `admin@stair-race.local`
     Firebase 이메일/비밀번호 방식은 계정 생성 시 메일이 실제로 존재하는지 확인하지 않으므로 형식만 맞으면 생성됩니다.
   - 단, 가상 이메일은 **비밀번호 재설정 메일을 받을 수 없습니다.** 잊어버리면 콘솔에서 사용자를 지우고 다시 만드세요.
4. 만든 이메일을 `config.js` 의 `adminEmail` 에 적어 두면 로그인 창에 미리 채워집니다 (편의 기능일 뿐, 권한과 무관).

## 4. Realtime Database 설정

1. **Realtime Database → 데이터베이스 만들기** (이미 있으면 그대로 사용). 위치는 가까운 지역(예: asia-southeast1) 권장.
2. **프로젝트 설정 → 일반 → 내 앱 → 웹 앱(</>)** 의 `firebaseConfig` 값을 `config.js` 의 `firebase` 에 복사
   - `databaseURL` 이 꼭 들어가야 합니다 (Realtime Database 화면 상단 주소).
3. 데이터는 전부 `stairRace/` 아래에 저장되므로 다른 게임 데이터와 섞이지 않습니다.

```
stairRace/
├─ admins/{uid}: true                     ← 콘솔에서 직접 입력 (관리자 지정)
├─ game/current                           ← 현재 경기: gid, status, seed, startedAt, countdownMs, durationMs, idleMs, endedAt, finalizedGid
├─ game/slots/{0~19}: uid                 ← 정원 관리
├─ game/players/{uid}                     ← 대기실: name, ch, slot, joinedAt, on, seen, ready
├─ game/runs/{gid}/{uid}                  ← 경기 진행: s(계단), d(방향), t(마지막 이동 서버시각), a(생존), n, c
├─ game/history/{gid}                     ← 경기 결과: finalLeaderboard, winnerUid ...
└─ playerStats/{uid}                      ← 개인 기록: gamesPlayed, wins, survived, bestStepCount, averageStepCount, recent
```

## 5. 보안 규칙 적용

**Realtime Database → 규칙(Rules)** 탭에 `database.rules.json` 내용을 붙여넣고 **게시**하세요.

> ⚠ **이미 다른 게임 규칙이 있다면 통째로 덮어쓰지 마세요.** 기존 규칙의 `"rules": { ... }` 안에 `"stairRace": { ... }` 블록만 추가해야 다른 게임이 계속 작동합니다.

예시:
```json
{
  "rules": {
    "기존게임경로": { ... 기존 규칙 그대로 ... },
    "stairRace": { ... database.rules.json 의 stairRace 블록 ... }
  }
}
```

규칙 안의 계단 방향 수식은 `game.js` 의 `isTurn()` 과 **반드시 같아야** 합니다. 둘 중 하나만 바꾸면 모든 이동이 거부됩니다.

## 6. 관리자 권한 설정

1. 게임 페이지 → **관리자** 버튼 → 3번에서 만든 이메일/비밀번호로 로그인
2. 창에 표시되는 **UID** 를 복사 (처음엔 "관리자 아님"으로 나옵니다)
3. Firebase 콘솔 → Realtime Database → 데이터에서 `stairRace/admins/<복사한 UID>` 를 만들고 값은 **불리언 `true`** (문자열 "true" 아님)
4. 게임 화면이 자동으로 "관리자 확인됨"으로 바뀌고 대기실에 관리자 메뉴가 나타납니다.

- 클라이언트는 `admins` 를 수정할 수 없습니다 (`.write: false`). 콘솔에서만 바꿀 수 있습니다.
- 관리자 버튼을 숨기는 것과 별개로, 시작·종료·기록 저장은 **규칙이 UID를 검사**하므로 일반 참가자가 콘솔로 직접 요청해도 거부됩니다.
- Custom Claims 는 Admin SDK(서버)가 있어야 설정할 수 있어서, 서버 없는 구조에서는 이 `admins` 목록 방식을 사용합니다. 보안 규칙에서의 효과는 같습니다.
- 관리자도 로그인 후 **참가하기**를 눌러 일반 참가자와 같은 규칙으로 플레이합니다 (특권 없음).

## 7. GitHub Pages 배포

1. GitHub 저장소에 `index.html`, `style.css`, `game.js`, `config.js` 업로드 (같은 폴더)
2. 저장소 **Settings → Pages → Build and deployment → Deploy from a branch → main / (root)** → Save
3. 1~2분 뒤 `https://<아이디>.github.io/<저장소>/` 로 접속
4. `config.js` 가 공개되지만 괜찮습니다. 웹 앱 설정값은 원래 공개용이고, 실제 보호는 보안 규칙이 합니다.

> 로컬에서 `index.html` 을 더블클릭하면 ES 모듈 제한 때문에 실행되지 않습니다. GitHub Pages 주소로 테스트하세요.

## 8. 조작 방법

| | 왼쪽으로 오르기 | 오른쪽으로 오르기 |
|---|---|---|
| PC | ← 또는 A | → 또는 D |
| 모바일 | 왼쪽 큰 버튼 / 화면 왼쪽 절반 터치 | 오른쪽 큰 버튼 / 화면 오른쪽 절반 터치 |

- 다음 계단이 놓인 방향을 누르면 한 칸 오릅니다. 틀리면 그 자리에서 추락(탈락).
- 키를 꾹 눌러도 한 번만 입력됩니다. 입력은 최소 80ms 간격으로 처리되고 최대 2개까지 미리 쌓입니다.
- 탈락하거나 시작 후 들어온 사람은 **관전**합니다. 순위표 이름을 누르면 그 사람을 따라갑니다.

## 9. 테스트 체크리스트 (요구사항 19번 대응)

준비: PC 브라우저 1개(관리자) + 휴대폰 1~2대, 또는 PC에서 **일반 창 + 시크릿 창**(서로 다른 참가자로 인식).

| # | 테스트 | 방법 / 기대 결과 |
|---|---|---|
| 1 | 비관리자 시작 시도 | 일반 참가자에겐 시작 버튼이 없음. 개발자도구 콘솔로 `game/current` 를 직접 써도 `PERMISSION_DENIED` |
| 2 | 관리자 시작 후 직접 참가 | 관리자가 참가 → 시작 → 3초 카운트다운 후 키보드로 오르기 |
| 3·4 | 20명 / 21번째 거부 | 20명 참가 후 21번째는 "정원(20명)이 가득 찼습니다" |
| 5·8 | 새로고침 복구 | 10계단쯤 오른 뒤 새로고침 → 같은 계단 수·캐릭터·방향으로 게임 화면 복귀 |
| 6 | 관리자 새로고침 | 경기 중 관리자 새로고침 → 남은 시간 그대로, 다른 사람 화면 정상 |
| 7 | 백그라운드 | 휴대폰에서 홈 화면으로 나갔다 오기 → 다른 참가자는 계속 진행. 돌아오면 무입력 시간 안이면 이어서 플레이, 넘었으면 탈락 표시 |
| 9 | 같은 코스 | 두 화면에서 계단 모양이 동일한지 비교 |
| 10~12 | 겹침 | 두 명이 같은 계단에 서면 둘 다 반투명(약 48%), 떨어지면 원래대로. 이동은 막히지 않음 |
| 13 | 틀린 방향 | 반대 방향 입력 → 추락 애니메이션, "방향을 틀려 추락했어요!" |
| 14 | 실시간 순위 | 순위표가 0.25초마다 갱신, 순위 바뀔 때 행이 미끄러지듯 이동 |
| 15 | 최종 순위 확정 | 시간 종료 또는 강제 종료 → 결과 화면, 관리자 화면에 "결과와 개인 기록이 저장되었습니다" |
| 16 | PC/모바일 조작 | 8번 표대로 |
| 17 | 서버 재시작 | 게임 서버가 없으므로 해당 없음. 대신 **관리자 포함 모든 참가자가 새로고침해도** 경기 상태는 Firebase에 남아 복구됨 |
| 18 | 계단 수 조작 | 콘솔에서 `runs/{gid}/{내UID}/s` 를 999로 쓰기 → `PERMISSION_DENIED` |

1·18번은 Firebase 콘솔 → Realtime Database → 규칙 → **규칙 플레이그라운드**로도 확인할 수 있습니다 (콘솔 데이터 탭에서 직접 수정하면 관리자 권한이라 규칙이 적용되지 않으니 플레이그라운드를 쓰세요).
- 유형: 설정(set) / 위치: `/stairRace/game/runs/<gid>/<참가자UID>/s` / 인증: 해당 UID / 값: `999` → **거부**되면 정상

## 10. 새로고침·백그라운드 복구 규칙

- **같은 브라우저**에서는 익명 로그인 UID가 유지되어 대기실 자리, 계단 수, 방향, 생존 여부가 그대로 복구됩니다. 중복 참가는 생기지 않습니다.
- **다른 기기나 브라우저 데이터를 지운 경우**는 새 UID가 되어 복구되지 않습니다 (새 참가자로 취급).
- **재접속 유예 = 관리자가 고르는 "무입력 탈락" 시간** (기본 60초, 5/10/30/60초 선택).
  이 시간 안에 돌아와 다음 계단을 누르면 이어서 진행, 넘기면 탈락 처리되고 그때까지 오른 계단 수로 순위에 남습니다.
  - 긴장감 있는 무한의 계단 스타일 → 5초
  - 연결이 불안정한 참가자를 배려 → 60초
- 대기실에서 연결이 끊긴 사람은 "오프라인"으로 표시되고 자리는 유지됩니다. 60초 이상 끊긴 사람은 관리자가 **오프라인 참가자 정리**로 내보낼 수 있습니다.
- 게임 진행은 `setInterval` 기반 틱으로 동작하고 `requestAnimationFrame` 은 그리기에만 씁니다.

## 11. 캐릭터 교체 (포켓몬 이미지 사용 시)

공식 포켓몬 이미지는 저작권 문제로 포함하지 않았고, 대신 오리지널 테스트 캐릭터 10종(해님냥, 민트토끼, 산호여우 …)이 들어 있습니다. 모든 캐릭터의 능력은 같습니다.
합법적으로 사용할 수 있는 이미지가 있다면:

1. `assets/` 폴더에 PNG 업로드 (투명 배경, 발밑이 아래 가운데, 오른쪽을 바라보는 그림 권장 — 왼쪽 이동 시 자동 좌우 반전)
2. `config.js` 의 `characterSprites` 에 연결: `sunny: "assets/파일명.png"`
3. 이름까지 바꾸려면 `game.js` 맨 위 `CHARACTERS` 배열의 `name` 을 수정 (`id` 는 그대로 두세요)

## 12. 알려진 한계 (솔직하게)

- **자동 입력 스크립트**: 계단 방향은 화면에 보여야 하므로, 스크립트로 허용 속도(초당 최대 25칸) 안에서 실수 없이 오르는 것까지는 막을 수 없습니다. 계단 건너뛰기·숫자 조작·부활·시간 외 이동은 규칙이 막습니다. 이벤트 상품이 크다면 상위권 기록은 화면 녹화로 한 번 확인하는 것을 권합니다.
- **틀린 방향 입력**은 "틀린 이동"이 규칙에서 거부되는 방식이라, 개조된 클라이언트는 틀려도 스스로 탈락을 기록하지 않을 수 있습니다. 다만 그 상태로는 다음 칸에 오를 수 없어 무입력 시간이 지나면 다른 화면에서 탈락으로 판정됩니다.
- **결과·개인 기록 저장**은 관리자 브라우저가 수행합니다. 경기 종료 시 관리자 창이 닫혀 있으면 경기와 순위는 정상 종료되고, 관리자가 다시 접속할 때 저장됩니다. **"다음 경기 준비"를 누르기 전에** 저장 완료 메시지를 확인하세요.
- 네트워크가 매우 느리면 내 화면이 서버보다 잠깐 앞서 갈 수 있고, 거부된 이동은 자동으로 서버 값으로 되돌아갑니다.
- 이 코드는 브라우저 자동화 테스트(가짜 DB)와 규칙 시뮬레이터로 검증했지만, **실제 Firebase 프로젝트 연결 테스트는 직접 해 보셔야 합니다.** 규칙 게시 단계에서 문법 오류가 나면 오류 위치를 알려 주세요.

## 13. 무료 요금제(Spark) 사용량 및 비용 주의

작성 시점 기준 Spark 요금제 Realtime Database 한도(정확한 수치는 [Firebase 요금 페이지](https://firebase.google.com/pricing)에서 확인):
**동시 연결 100개 · 저장 1GB · 다운로드 월 10GB.** Spark는 한도를 넘으면 과금되지 않고 해당 기능이 멈춥니다.

이 게임의 다운로드 사용량 추정 (모든 이동이 모든 참가자에게 전달되는 구조):

| 조건 | 1경기(180초) 다운로드 | 월 10GB로 가능한 경기 수 |
|---|---|---|
| 20명, 1인 평균 초당 5칸 | 약 50~80MB | 약 120~200경기 |
| 10명, 1인 평균 초당 5칸 | 약 15~20MB | 약 500경기 이상 |

- 사람 수가 2배면 사용량은 약 **4배**(보내는 사람 × 받는 사람)입니다.
- 같은 Firebase 프로젝트를 쓰는 **다른 게임과 한도를 공유**합니다. 동시 연결 100개도 모든 게임 합산입니다.
- 사용량은 콘솔 → Realtime Database → 사용량 탭에서 확인하세요.
- 경기 후 "다음 경기 준비"를 누르면 경기 진행 데이터(runs)가 삭제되어 저장 용량이 쌓이지 않습니다. 결과(history)와 개인 기록은 남습니다.
- Blaze(종량제)로 바꾸면 한도 초과분이 과금되므로 예산 알림을 꼭 설정하세요.
